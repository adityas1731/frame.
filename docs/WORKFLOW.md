## 2. Build A Local Plugin Update

1. Choose an unused four-part version in `frame.json`. Update `releaseNotes` and `CHANGELOG.md`.
2. Run `node scripts/sync-version.mjs`. Review `git diff` and `git status`, then commit only the intended source files. Do not include local data, credentials or build outputs.
3. Run the complete existing pipeline:

```powershell
pwsh -File scripts/dev.ps1 package
```

Use the pinned Node and .NET SDK versions in `frame.json`. Set `$env:FRAME_DOTNET` to an existing local `dotnet.exe` if it is not on PATH. Dependency installation is a setup step, not part of each UI edit. See [Build](BUILDING.md).

The pipeline tests both profiles, TypeScript, host policies, publication guards, resource isolation and plugin compilation. Pick the **Release** ZIP matching your new version in `jellyfin-plugin/artifacts`. Keep Internal Diagnostics out of distribution.

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath '<exact Release ZIP path>'
pwsh -File jellyfin-plugin/scripts/verify-package.ps1 `
  -Archive '<exact Release ZIP path>' -Profile release `
  -ExpectedVersion '<four-part version>' -ExpectedCommit '<full build commit>' `
  -ExpectedSha256 '<SHA-256>'
```

### Install On Your Server

This is a separate manual action. Building alone never installs anything.

1. Stop all playing and paused sessions. Stop Jellyfin through its normal tray/service controls.
2. Make a **fresh backup** of the actual Jellyfin data/configuration and installation directories, including plugins. Use a new destination. On Windows use Robocopy `/E /COPY:DAT /DCOPY:DAT /XJ /R:2 /W:2`, never `/MIR`. This preserves data, attributes and timestamps, not ACLs, ownership or auditing metadata.
3. Verify copy logs, complete relative-file coverage and SHA-256 for **every copied file**. Stop on unreadable content or mismatches. Keep the old Frame directory outside the live plugins directory for rollback. Do not install from an incomplete backup.
4. Extract the verified Release ZIP into `plugins/Frame_<version>/`. `Frame.Jellyfin.dll` must be directly inside. Keep only the intended Frame version active. Do not alter other plugins or original Jellyfin Web files.
5. Start Jellyfin normally. Check startup logs, installed version, `/Frame/Web/`, `/web/` and plugin resources. Test playback separately when ready.

If startup or resource checks fail, stop Jellyfin, move the new Frame directory outside `plugins`, restore the previous Frame directory and restart. Use plugin-only rollback, not an unrelated database restore.

## 3. Release Through The Catalog

```text
Reviewed commit → both-profile validation → source/package verification
→ branch push and CI → reviewed main integration → seven-asset draft
→ verify-only workflow → explicit publication → catalog → user installs/restarts
```

Use the same verified binary throughout. Do not rebuild it under the same published version. [Publication](PUBLICATION.md) gives the draft commands and final manual gate.

Before staging, prepare and review `release/<version>.json`, its source map and versioned catalog file. These are release records, **not generated by the UI preview or package command**. The seven assets are the Release ZIP, corresponding-source ZIP, dependency-source ZIP, GPL license, UI notices, plugin notices and `SHA256SUMS`. Verify source completeness and licensing, repeat the build in a clean checkout to check reproducibility, and test catalog installation in disposable Jellyfin. Reuse dependency sources only after proving the dependency locks and notices have not changed.

Commit the release records after the build commit. The receipt keeps the original build commit; the draft points to the final main revision containing those records. Verify implementation hashes still match. A green CI run from another revision does not qualify.

**Three different results:** Vite updates only your preview. Local installation updates only that server. Publishing updates the catalog and makes a plugin update available to other servers. It never deploys to them automatically from this repository.
